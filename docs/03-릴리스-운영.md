# QuickDeck 릴리스 운영

v0.1.5 부터 QuickDeck 은 GitHub Releases 로 자동 업데이트한다. 이 문서는 새 버전을 안전하게 내는 절차와 규칙이다.

## 구조

- 업데이트 확인 주소(앱에 고정): `https://github.com/lohemal/QuickDeck/releases/latest/download/latest.json`
  - GitHub 의 "latest" Release(초안·사전 배포 제외) 의 `latest.json` 으로 연결된다. REST API 가 아니라 웹 다운로드 경로라 API 횟수 제한과 무관하다.
- Release 하나에는 반드시 다음 세 파일을 올린다.
  | 파일 | 용도 |
  |---|---|
  | `QuickDeck_<버전>_x64-setup.exe` | 처음 설치·수동 업데이트·자동 업데이트에 같은 파일을 쓴다 |
  | `QuickDeck_<버전>_x64-setup.exe.sig` | updater 서명 (minisign, Ed25519) |
  | `latest.json` | 버전·서명·태그 고정 다운로드 주소 |
- updater 서명 키: 공개키는 `src-tauri/tauri.conf.json` `plugins.updater.pubkey` (key ID `A9D1D4D7500BFEFF`). 비밀키 `%USERPROFILE%\.tauri\quickdeck-updater.key` 는 저장소 밖에 두고 백업 2곳에 보관한다. 비밀키나 비밀번호를 잃으면 기존 설치본에 더 이상 업데이트를 보낼 수 없다.
- Windows 코드 서명(Authenticode)은 없다. updater 서명과는 별개다.

## Release 불변(immutable) 정책

- 저장소 설정 **Release immutability 가 켜져 있다** (2026-11-20 부터). 켠 뒤 Publish 한 Release 는 asset 과 태그를 바꿀 수 없다. 제목·노트·latest 지정은 바꿀 수 있다.
- 켜기 전에 공개한 v0.1.4, v0.1.5 에는 소급되지 않는다. 그래도 같은 원칙으로 다룬다: **이미 공개한 asset 은 절대 교체·삭제하지 않는다.**
- Publish 한 뒤 asset 에 문제가 있으면 고치지 않고 **새 patch 버전**(예: 0.1.6 → 0.1.7)으로 다시 낸다.
- 불변 Release 는 삭제할 수는 있지만 그 태그 이름은 다시 쓸 수 없다. 그러므로 Release 를 지우고 같은 버전으로 다시 내는 방식은 쓰지 않는다.
- 불변 Release 에는 GitHub 가 release attestation(태그·커밋 SHA·asset 기록)을 자동으로 만든다.
- updater 파일이 없는 Release 를 latest 로 공개하지 않는다. 공개하는 순간 모든 사용자의 업데이트 확인이 404 가 된다(그런 Release 는 latest 로 지정하지 않는다).

## 새 버전 내는 절차

1. **버전 올리기**: `package.json`, `package-lock.json`(루트 2곳), `src-tauri/tauri.conf.json`, `src-tauri/Cargo.toml` 을 같은 SemVer 로. `Cargo.lock` 은 빌드 때 따라온다.
2. **검사**: `npx tsc --noEmit`, `npm run check`, `npx vite build`, `cd src-tauri && cargo test` 모두 통과. 커밋.
3. **서명 빌드** (PowerShell, 이 세션에만 키 경로를 둔다. 비밀번호는 빌드가 물을 때 입력):
   ```powershell
   $env:TAURI_SIGNING_PRIVATE_KEY = "$env:USERPROFILE\.tauri\quickdeck-updater.key"
   npm run app:build
   Remove-Item Env:TAURI_SIGNING_PRIVATE_KEY
   ```
   결과물: `src-tauri/target/release/bundle/nsis/` 의 setup.exe 와 .sig. 빌드 시각이 마지막 커밋보다 뒤인지, 앱 본체에 정식 endpoint 만 들어 있는지 확인한다.
4. **latest.json 만들기** (공개 직전 시각으로):
   ```
   node --experimental-strip-types --no-warnings scripts/make-latest-json.ts --notes "릴리스 요약"
   ```
   이 스크립트가 .sig 를 공개키로 검증하고, BOM 없는 UTF-8·`windows-x86_64` 한 항목·태그 고정 URL(`/releases/download/v<버전>/…`)·signature 일치를 확인한다. PowerShell 로 latest.json 을 직접 쓰지 않는다(BOM 이 붙으면 업데이트 확인이 실패한다).
5. **push 와 태그**: main 을 force 없이 push. annotated 태그 `v<버전>` 을 그 커밋에 만들고 태그만 push.
6. **Draft Release**: 태그 `v<버전>` 으로 **Draft** 를 만들고 세 파일을 올린다. prerelease 로 표시하지 않는다.
7. **Draft 검증** (하나라도 다르면 Publish 하지 않는다):
   - 세 asset 의 이름·크기와 GitHub 가 보여 주는 digest(sha256) == 로컬 SHA
   - .sig 공개키 검증 VALID, latest.json 의 signature == .sig 전체 내용, version, URL
8. **Publish** (latest 로 지정). Publish 후에는 asset 을 바꾸지 않는다.
9. **공개 확인** (로그인 없이):
   - `…/releases/latest/download/latest.json` → 302 → 200, 새 버전
   - installer·.sig 를 다시 받아 SHA 가 로컬·digest 와 같은지, 서명 VALID 인지
   - 이전 버전 설치본에서 업데이트 배너 → 업데이트 → 새 버전 실행 · 데이터 유지 확인

## 업데이트 동작 요약 (앱 쪽)

- 시작 5초 뒤 한 번만 확인(설정에서 끌 수 있음), 반복 확인 없음. 실패는 조용히.
- 설치는 사용자가 [업데이트] 를 눌렀을 때만: 입력 차단 → 저장 freeze → 기다리던 저장 flush → 내려받기·서명 검증 → NSIS passive 설치 → 새 버전이 다시 열린다(`--updated`). 실패하면 freeze 를 풀고 계속 쓸 수 있다.
- 서명이 맞지 않으면 설치하지 않는다(끌 수 없음). 다운그레이드는 제안하지 않는다.

## 기록: P14-C 실제 업데이트 검증 (2026-11-19)

공개 전, 별도 공개 저장소 `lohemal/QuickDeck-update-test` 에 테스트용 v0.1.6 Release(installer SHA `473E9677C6F975131DD6D263DC403B9D635122DF20686D5629693702F0BB59F3`, 같은 updater 키로 서명)를 올리고, 테스트 endpoint 를 가리키는 v0.1.5 테스트 빌드를 이 PC 에 설치해 실제 GitHub HTTPS 로 v0.1.5 → v0.1.6 업데이트를 검증했다. 정식 소스·설정은 바꾸지 않았다(빌드 시 `--config` 로만 endpoint 를 바꿈). 검증 후 테스트 저장소는 삭제하기로 했다(2026-11-20 승인).

| 항목 | 결과 |
|---|---|
| 자동 확인 | 시작 6.8초 뒤 1회, v0.1.6 배너. 시작을 막지 않음 |
| 수동 확인 / 나중에 | 클릭마다 1회 / 배너만 닫힘, 설치 없음 |
| 서명 | 정상 서명 설치 성공. 다른 파일의 서명을 붙인 실제 HTTPS 다운로드는 설치 거부, installer 미실행 |
| 설치 흐름 | 다운로드 → 저장 flush → `installer /P /UPDATE /R /ARGS --autostart --updated` → 기존 프로세스 종료 → 새 프로세스(`--autostart --updated`) 창 표시. 클릭부터 새 창까지 약 6.4초 |
| 데이터·Run | 업데이트 전후 사용자 데이터·아이콘 SHA 유지(사용자가 바꾼 값만 반영), HKCU Run 값 동일 |
| 단일 인스턴스·단축키 | 업데이트 후 프로세스 1개, 단축키 정상 |
| 최신 상태 | v0.1.6 에서 "최신 버전입니다", 업데이트 반복 없음 |
| 404 | 조용히 실패, 수동 확인만 안내 |
| SmartScreen | 업데이트 installer 실행 시 표시되지 않음(이 PC, MOTW 없음 — 모든 환경을 보장하지는 않음) |
| 네트워크 | 확인 1회당 github.com + release-assets 연결, 60초 대기 동안 0건 |

이 검증에서 찾은 "저장 flush 뒤 종료 전 1~2초 사이 변경 유실" 은 P14-D(입력 차단·저장 freeze)로, 이어서 찾은 "저장 실패 후 재시도 한계" 는 P14-E(제한된 재시도·안내·종료 확인)로 고친 뒤 v0.1.5 를 공개했다.
